# The renderer

How Paleblood puts Bloodborne's frames on screen: Vulkan on Linux, Metal on macOS. This is the
plan the maintainer chose on 4 November 2026 (issue #39), and where each part stands.

## The approach

Bloodborne draws through its own engine renderer (the `GX` framework) and Sony's GPU helper
library compiled into the game (`GfxContext`). Together they turn each draw into GPU command
buffers, which the game then hands to the system. Its shaders ship as compiled AMD GPU code
(GCN, the PS4 GPU's instruction set) inside its `.shaderbnd` bundles.

Paleblood does not emulate the PS4's GPU, and it does not replay the finished command buffers.
Instead:

- **Engine draw hooks.** The game's own draw layer is replaced function by function, the same way
  as the rest of the decompilation. Render targets, clears, shader binding, buffers, textures,
  state and draws go to Paleblood's renderer instead of into command buffers.
- **Shader translation.** Each shader the game loads is translated from GCN code to SPIR-V for
  Vulkan, and to MSL for Metal. The translator is written clean-room from AMD's public
  instruction-set manuals; no emulator's translator is consulted or modelled. Translation runs on
  your machine from your own copy of the game, and nothing translated is committed or published.
- **Until the hooks draw,** GPU work goes through the temporary stand-in in
  `runtime/syslib/gnm.c`. It completes each submission at once so start-up can continue, and it
  draws nothing.

## Phases

1. **Display** (this phase). Every frame buffer the game registers with video out has a host
   frame, and each flip shows it (`runtime/display/`, `runtime/display.h`).
   - `pbboot --display window` opens a window, with SDL3 and Vulkan.
   - `--display headless` keeps and counts the frames.
   - `--display-capture DIR` writes every presented frame as a PPM image, for tests and for
     looking at a run.
   - `tools/boot.py` passes both options on. The default, `none`, leaves boots as they were.
   - Today the frames are black: nothing draws into them yet. macOS gets a Metal window next
     (building on the offscreen Metal unit of #213).
2. **Shader translator** (in progress).
   - **Decoder** (done): `runtime/renderer/gcn_decode.c` (`runtime/gcn.h`). It splits code into
     instructions, with sizes, literal constants and the VOP3 forms of the 32-bit vector
     encodings, names each one, and finds where a shader binary's program ends.
     - The GFX7 opcode table, `runtime/renderer/gcn_opcodes.inc`, is generated by
       `tools/gcn_tables.py` from two public sources that must agree: the Sea Islands manual and
       LLVM's AMDGPU assembler. LLVM only disassembles GFX8 and later, so GFX8's instruction names
       are listed first, then each is assembled for GFX7.
     - `test/test_gcn.c` checks instructions LLVM assembled for GFX7.
   - **Census** (done): `game/render/tools/shader_census.py` decodes the shaders in your own copy
     with `build/pbgcn` and prints instruction counts only; no game code or data leaves your
     machine.
     - Today every instruction the game's shaders use is in the table: 175 distinct instructions
       across about four million.
     - A few shader entries start earlier than their information block's length says, and a few
       hold no program. Reading the archive's own entry table will settle both.
   - **Translator** (begun): `runtime/renderer/gcn_spirv.c` (`runtime/gcn_spirv.h`), with a small
     SPIR-V module builder (`runtime/renderer/spirv.c`).
     - **How GCN maps onto SPIR-V:**
       - one invocation per lane;
       - registers are 32-bit words, and float operations reinterpret their bits;
       - a compare or carry result kept as the lane's own bit;
       - memory reached through the base addresses in buffer descriptors, as SPIR-V
         physical-storage-buffer pointers.
     - **Control flow:** the program is split into basic blocks, run as cases of a switch inside
       a loop (a structured form that SPIR-V accepts for any branch pattern).
       - EXEC is each lane's own "active" bit. Only active lanes write registers or touch memory,
         and compares write 0 for inactive lanes, as on GCN.
       - SCC follows each scalar instruction's definition in the manual. The 64-bit mask
         operations (`s_and_saveexec` and the like) work on the lane bits.
       - "Is any lane set" tests (EXECZ, VCCZ, a mask result's SCC) use a Vulkan subgroup vote.
         That is exact when the subgroup is GCN's 64-lane wave; with smaller subgroups (32 on
         NVIDIA) each one decides for itself.
     - **Translated so far:** compute shaders with branches and loops. That covers float and integer
       arithmetic (including GCN's legacy multiply, where zero times anything is zero),
       conversions that saturate as GCN's do, compares and selects, integer carries, scalar
       arithmetic, and buffer and constant loads and stores.
     - **VCC's halves:** a scalar write of `VCC_LO` or `VCC_HI` (s106, s107) gives the 32 lanes of
       that half of the wave their bits of the value. VCC is kept as each lane's bit, and a compute
       lane's place in its wave is its flat index in the workgroup mod 64 (x fastest), so this is
       exact in compute shaders; other stages stop by name, as does reading VCC as a scalar.
     - **VCC outside compute shaders:** a lane has no known place in the wave there, so a scalar
       write of VCC's halves leaves each lane's VCC bit unknown until a vector write sets it; reading
       VCC as a lane mask while unknown is a run-time stop. The game's vertex shaders write `vcc_hi`
       before vector adds overwrite VCC, so they translate.
     - **Whole quad mode** (`s_wqm_b64`): a lane's bit is set when any lane of its quad has it,
       with Vulkan's quad swaps (the same 2x2 pixel quads in a pixel shader, consecutive lanes in
       compute); SCC is "any lane set". Every invocation, helpers included, starts with EXEC set.
     - **Pixel position inputs** (`SPI_PS_INPUT` bits 8 and 9): x and y at the pixel's centre from
       `FragCoord`. The executor places each pixel input in bit order of `SPI_PS_INPUT_ADDR` with
       AMD's sizes (2 VGPRs per barycentric pair, 3 for the pull model, 1 for the rest), as AMD's
       register documentation and LLVM's AMDGPU backend have it.
     - **Run-time stops:** some of what a shader does is known only when it runs (a buffer access's
       data format is its descriptor's). The executor owns a 32-bit stop word for each translated
       shader, whose GPU address is baked into its translation (`error_address`); a shader meeting a
       case it cannot do exactly writes a code there and skips the access, and the executor checks
       the words once the work has run and stops by name (`GCN_RUNTIME_STOP_*`), naming the shader.
     - **Format buffer accesses** (`buffer_load/store_format_*`): loads of 8- and 16-bit components
       (8, 16, 8_8, 16_16, 8_8_8_8, 16_16_16_16) as uint (zero-extended), sint (sign-extended) and,
       for 8-bit components, unorm (each byte v / 255, correctly rounded), read byte by byte from any
       alignment, x first and little-endian; whole 32-bit components (uint,
       sint, float; the format's components in place, as a store only uses their selectors) move as they are, and a four-component store to 8_8_8_8 unorm
       undoes the descriptor's swizzle (shadPS4's rule: the inverse of a load's) and packs as GLSL's
       `packUnorm4x8` (the PS4's rounding of ties is not established). Anything else is a run-time stop. A descriptor of DATA_FORMAT 0 (invalid, a null buffer's) reads 0 and writes nothing. A four-component store to 16_16_16_16 float packs halves, and one to 10_11_11 float unsigned
       11-, 11- and 10-bit floats (x in the low bits), rounded to nearest even.
     - **VOP3 output modifiers** on float results: OMOD multiplies by 2, 4 or 0.5, then the clamp
       to [0, 1] applies.
     - **Cube instructions** (`v_cubeid_f32`, `v_cubesc_f32`, `v_cubetc_f32`, `v_cubema_f32`): the
       face a direction's largest component picks (z, then y, then x on ties), its number, s and t
       before division and twice the major axis, as shadPS4 computes them without native cube
       instructions; shaders then take s / |ma| + 1.5 and t / |ma| + 1.5.
     - **Format loads with a swizzle:** a load of whole 32-bit components reads the format's
       components (the ones it lacks read 0), then each result takes what its DST_SEL names: 0, 1
       (1.0 for float data) or a memory component, as shadPS4 reads them.
     - **Images (MIMG `image_load`, `image_store`):** a shader names an image by the SGPRs holding
       its 8-word descriptor. `gcn_image_resources` lists them; the caller reads each descriptor
       (`rt_image_descriptor_decode`, the Sea Islands manual's T# layout as shadPS4's `resource.h`
       has it) and binds a storage image (set 0, binding i) whose shape the translation uses. Stores
       must cover every component the format has; data components past them are dropped.
       The executor keeps what shaders store in the image (it is not written back to memory). When
       a shader stores into a render target's memory (a compute clear, as the game clears its
       G-buffer), the target's next draw first copies the image's texels into the target (an
       8_8_8_8 image into an 8_8_8_8 target, otherwise the same format; at least the target's size),
       and the image loads from memory again at its next use; an image over a target's memory loads
       it even when only written, so a store that covers part of it keeps the rest.
     - **Pixel shaders read images** (`image_load`, `image_load_mip`) as sampled images (Vulkan's
       `SAMPLED_IMAGE`, `OpImageFetch` at the level given), so the view applies the descriptor's
       DST_SEL. A texel outside the image or a level past its last is a run-time stop
       (`GCN_RUNTIME_STOP_IMAGE_RANGE`): what the GPU returns there is not established.
     - **Mip-mapped images** (a pixel shader's sampled images, BASE_LEVEL to LAST_LEVEL): the
       executor makes the image with LAST_LEVEL + 1 levels and views BASE_LEVEL on. Each level's
       texels come from where `rt_tiling_mip_chain` (runtime/tiling.h) puts them: the levels one after
       another, each rounded to a power of two with POW2_PAD; a 2D-tiled image's levels macro tiled
       while they span a macro tile, smaller ones (and every 1D-tiled level) micro tiled with 256-byte
       slices (AMD's address library for GFX7, as shadPS4's `ComputeImageSize` follows). The levels
       are detiled by the CPU. `image_load` and `image_load_mip` read them exactly, `image_sample`
       at the level its derivatives pick (below). A storage image keeps one level.
     - **Cube images** (T# TYPE 11) in pixel shaders: a 2D array of six faces per cube (DEPTH counts
       whole cubes), viewed whole. Sampling takes (s, t, face), whatever DA says: the cube
       instructions leave s and t in [1, 2], so the face's coordinates are one less, and the face
       number counts 8 per cube of an array (as shadPS4 samples cubes as 2D arrays). Filtering does
       not cross faces.
     - **`image_sample_l`** takes its level of detail after the coordinates and samples there
       (Vulkan's explicit `Lod`, which the sampler's LOD bias and clamps still adjust).
     - **`image_sample`** with the sampler (S#) its SSAMP SGPRs name, found like image descriptors and
       bound after the images (set 0, `VK_DESCRIPTOR_TYPE_SAMPLER`): sampled at the level the
       coordinates' derivatives pick, as GCN does: the derivatives across the pixel's 2x2 quad (x from
       the quad's first lane to its second, y to its third, by `OpGroupNonUniformQuadBroadcast`),
       passed as explicit gradients (`OpImageSampleExplicitLod` with `Grad`), since the translated
       program's dispatch loop is not uniform control flow for Vulkan's implicit derivatives. The
       sampler's LOD bias, MIN_LOD and MAX_LOD (8 fraction bits) and mip filter (none: the view's first
       level, with a maximum LOD of 0.25 so the minifying filter still applies; point; linear) go to
       the Vulkan sampler, and the minifying and magnifying filters may differ. Anisotropic filters (2 point, 3 bilinear) are their
       point or bilinear filter with Vulkan's anisotropy up to MAX_ANISO_RATIO's 1-16 samples, within
       the device's limit (ANISO_THRESHOLD and ANISO_BIAS are not used). The executor makes a Vulkan sampler from the S#
       (the Sea Islands manual's layout, as shadPS4's `resource.h` names its fields): wrap, mirror
       and clamp to the last texel; point or bilinear filtering. The anisotropy fields are accepted with point or
       bilinear filters, which they do not affect; anisotropic filters, depth compares,
       unnormalized coordinates, border and mirror-once modes and the truncation options stop by
       name, as does bilinear sampling of a format the device cannot filter. Filtering precision is
       the host GPU's.
     - **Descriptors from memory:** each MIMG instruction's descriptor is found from the code before
       it (`gcn_resource_origin`): the user data's when nothing writes its SGPRs first, or loaded
       from memory when the last write is an `s_load_dwordx8` (or a wider load that covers the
       descriptor's SGPRs, as the game's `s_load_dwordx16` of two image descriptors) at an immediate offset from a
       user-data pointer pair that nothing writes before it. The executor reads such a descriptor from guest
       memory when the draw runs. The same SGPRs can name different images at different
       instructions: the game's fullscreen pass reads the user data's image, then loads another
       descriptor over it. With branches in the program a load is followed only when every path to
       the instruction passes it: no branch lands between the load and the use, every branch target
       is known, no loop goes back to the use after a later write to those SGPRs, and, when a branch
       goes back to the load or before it, nothing at all writes the pointer pair (without one, code
       after the load may reuse the pointer's SGPRs, as the character creation preview's pixel
       shaders do once their samples are done). Writes before the load do not matter (the game's guarded samples keep a
       compare's mask there, then branch over the load and the use together). The user data's descriptor holds at a use no write comes before, whatever
       forward branches run (the game's shaders reuse a sampler's SGPRs after their last sample).
       Any other write (a scalar
       move, a compare's result, a written pointer) stops by name.
     - **Tiled layouts** (`runtime/tiling.h`): where each texel of an image lies in guest memory, for
       reading images the CPU or a shader's buffer stores wrote. AMD's address library (addrlib, in
       Mesa) gives the formulas; the PS4's tile-mode and macro-tile-mode values are those shadPS4's
       `tiling.cpp` lists (8 pipes, P8_32x32_16x16, a 256-byte pipe interleave, no bank swizzle on the
       base PS4). Done: linear (tiling indices 8, 31), 1D thin (9, 13) and 2D thin (10, 14), one
       sample, 1 to 16 bytes per element; others are refused by name. `test/test_tiling.c` checks
       offsets worked out by hand, mutated layouts that must miss them, shadPS4's table of macro-tile
       sizes, and that every layout is a permutation of the image's bytes.
     - **Descriptor base addresses are 40 bits** (word 1's bits 0-7; the Sea Islands manual's Table
       8.5 as shadPS4's `resource.h` lays it out). The game sets word 1's bits 8-15, which the
       translator used to take as address bits, sending the GPU outside guest memory.
     - **Buffer range checking**: every MUBUF/MTBUF access is checked against its descriptor's range
       as the hardware does (CLRX's GCN memory handling notes, gem5's GCN3 model): out of range a
       load reads 0 and a store writes nothing, dword by dword. Stride 0: NUM_RECORDS (word 2) counts
       bytes and the offset must be below NUM_RECORDS less the SGPR offset; with a stride and an index,
       the index must be below NUM_RECORDS and the offset below the stride; a strided access without
       an index is held to NUM_RECORDS records. Without it a vertex shader indexing a table with an
       index from its vertex data (the main menu's last draw after New Game) sent the GPU far outside
       the guest memory, and the NVIDIA driver reset the context (Xid 109, `CTX SWITCH TIMEOUT`); out
       of range stores could write anywhere in guest memory.
     - **Typed buffer loads and stores** (`tbuffer_load_format_*`, `tbuffer_store_format_*`):
       the format is in the instruction. The game uses only 32-bit float data (one to four
       components, as many as the access names), which moves whole dwords with no conversion, so
       only that is translated. Any other format, or an access with more components than its
       format has (whose missing components get default values), stops with the format's
       numbers. The descriptor's destination swizzle is not applied yet.
     - **More arithmetic:** 24-bit multiplies (`v_mul`/`v_mad` `i32_i24`, `u32_u24`), bit fields
       (`v_bfe`, `s_bfe`, `v_bfm`), add and subtract with carry (`v_addc_u32`, `v_subb_u32`,
       `v_subbrev_u32`), scalar compares with a 16-bit constant (`s_cmpk_*`: zero-extended for
       u32, sign-extended for i32), scalar min and max, sine and cosine (whose operand counts
       whole turns), base-2 `v_exp_f32` and `v_log_f32`, and `v_rsq_clamp_f32` (the largest float
       instead of infinity). Cases GLSL leaves undefined (the log of zero or of a negative number,
       the reciprocal square root of a negative number) are spelled out as IEEE defines them.
     - **Vertex and pixel shaders** (`gcn_translate_vertex`, `gcn_translate_pixel`):
       - **Exports (`exp`):** a vertex shader's `pos0` becomes the position and `param` n the
         output at location n; a pixel shader's `mrt` n becomes colour output n. Only the enabled
         components are written, and only by active lanes. A compressed export carries two halves
         per VGPR (made by `v_cvt_pkrtz_f16_f32`, which rounds toward zero exactly as defined,
         subnormals and overflow included). With the valid-mask bit, a pixel whose lane is not in
         EXEC is discarded.
       - **`pos1`-`pos3`** carry what the shader's `PA_CL_VS_OUT_CNTL` enables, in the order it
         defines: the misc vector, then clip/cull-distance vectors 0 and 1. The vertex layout
         takes that register value (`output_control`). Clip distances become SPIR-V's
         `ClipDistance`; the misc vector (point size and the like) and cull distances stop
         translation by name, as does the depth target.
       - **Inputs:** a vertex shader gets the vertex index in the VGPR its layout names. A pixel
         shader's `v_interp_p1`/`p2` pair reads attribute n at location n, interpolated by the GPU
         with perspective at the pixel centre; the layout names the VGPRs that hold those
         barycentrics. GCN computes the pair in two halves, so here `p1` already writes the finished
         value and `p2` must follow it into the same VGPR. Other interpolation modes,
         `v_interp_mov` and other pixel inputs stop translation.
       - **Matching the stages:** parameter n of the vertex shader feeds attribute n of the pixel
         shader. The console maps them through GPU settings; the engine hooks will set that up.
     - **Calls to fetch shaders** (`s_swappc_b64`): the game's vertex shaders call a fetch shader at
       the address in a user-data SGPR pair, which loads the vertex inputs and returns with
       `s_setpc_b64`. The executor reads that address at draw time (`gcn_call_sgpr` names the pair:
       user data untouched before the call, one call) and the translator inlines the callee in place
       of the call, the return pair taking the return address. That is exactly what the call runs
       when the callee is straight-line code ending in that return, which it checks; a callee with a
       branch, an image instruction or a write to the return pair stops by name. Descriptor analyses
       take a call as writing every SGPR.
     - **Not yet:** anything else stops with the instruction's name. Three groups need designs of their own:
       - **geometry shaders**, which pass vertices on with `s_sendmsg` (about 1,700 of the
         game's shaders);
       - the GPU's on-chip shared memory (`ds_*`);
       - reads across lanes (`v_readlane`, `v_writelane`, `ds_swizzle`), whose results depend
         on GCN's 64-lane wave where Vulkan and Metal GPUs often run 32 lanes.
     - **Tests:** `test/test_gcn_spirv.c` checks every module with `spirv-val` for Vulkan 1.2.
       `test/test_gcn_compute.c` runs programs on a Vulkan device and compares every output word
       with values worked out by hand from the manual. `test/test_gcn_draw.c` draws a triangle
       with a translated vertex and pixel shader and checks every pixel.
   - **macOS:** the same SPIR-V becomes Metal's shader language through SPIRV-Cross, the Khronos
     project's converter. Its buffer pointers become Metal device pointers and its subgroup votes
     `simd_any`, so one translator serves both platforms. Metal 2.3 or later (macOS 11) is needed.
     - `test_gcn_spirv` converts every translated test program with SPIRV-Cross when it is
       installed.
     - The `macos-metal` CI workflow also compiles each result with Apple's Metal compiler.
3. **Engine draw hooks.** Map the draw layer: the shader-binding helpers at
   `0x01475400`–`0x01475a70` and their callers, the render-target, clear, viewport, blend and draw
   entry points. Then route them to the renderer. The first target is the title screen's 2D
   passes: clears, textured quads and text.
   - **Map, first pass** (begun): `tools/pm4_writers.py` lists the functions whose code holds GPU
     command-packet headers, and names each register a packet sets. It uses AMD's GFX7 register
     header from the Linux kernel (`gca/gfx_7_2_d.h`, MIT licensed); the opcodes are those of
     the kernel's `cikd.h`. On the game's executable:
     - **One block holds the GPU library.** 231 of the 232 packet-writing functions lie in
       `0x01472000`–`0x0148ffff`, Sony's GPU helper library compiled into the game. The engine
       writes no packets of its own (one function elsewhere holds a header), so everything the
       game asks of the GPU passes through that library's functions.
     - **Draws:** `DRAW_INDEX_2` at `0x014740a0` and `0x01474360`, `DRAW_INDEX_AUTO` at
       `0x014741b0` and `0x01474250`, `DRAW_INDEX_OFFSET_2` at `0x01474420`, `INDEX_TYPE` at
       `0x01475270`, `NUM_INSTANCES` at `0x014728d0` and `0x01475370`.
       - `0x014741b0` takes (command buffer, index count). It writes `DRAW_INDEX_AUTO` with
         draw initiator 2 (auto index), then possibly an `EVENT_WRITE`.
       - **The command buffer object:** its end at `+0x08`, the write cursor at `+0x10`, a
         callback that makes room (with its argument) at `+0x18`/`+0x20`, and flags at `+0x28`
         (bit 0 the packets' predicate bit).
     - **State setters:** about 60 one-register setters, each writing one context register, such
       as `DB_DEPTH_CONTROL`, `CB_COLOR_CONTROL`, `CB_TARGET_MASK`, `CB_BLEND_RED` (blend
       colour), the window and generic scissors, `PA_SU_SC_MODE_CNTL` (culling and fill),
       `PA_CL_CLIP_CNTL`, `PA_CL_VTE_CNTL` and `DB_STENCIL_CONTROL`, plus the shader stages'
       binders above. Render targets and viewports are written with counts the code computes, so
       the header search does not find them yet.
     - **Callers:** the draws are called from a few engine wrappers at `0x015fbb50`-
       `0x015fbcc0` and from `0x0073e640`-`0x0073e6b0`, `0x025696c0`-`0x02569900`,
       `0x025d5f80` and `0x02ab55a0`-`0x02ab6cb0`. `0x015fbb50` (auto-index draws) alone has
       seven callers in `0x015e7db0`-`0x015eb850`.
   - **What it means for the hooks:** the GPU state (render targets, blending, depth, scissors)
     exists only as packets those setters write; the engine keeps no copy to read. So the hooks
     sit on the library's setters and draws: each setter records its value for the renderer
     instead of writing a packet, and each draw makes a Vulkan or Metal draw with the recorded
     state and the translated shaders. That is the library's own interface, call by call, not a
     replay of the packets. The binders' register blocks also give what the translator's layouts
     need: where each shader's code starts, its input VGPRs, and the vertex-output control that
     says what `pos1` carries.
   - **The key entry points** (from their disassembly; several are decompiled in open PRs):
     - **`setRenderTarget`, `0x014738b0`:** (command buffer, slot, render target). It writes 11
       context registers from `CB_COLOR0_BASE + 15 × slot` (base address, pitch, slice, view,
       format info, attributes and the compression metadata), straight from the render target's
       first 11 words. A null or invalid target writes `CB_COLORn_INFO = 0` instead, which
       switches the slot off.
     - **The depth render target, `0x014739b0`:** `DB_Z_INFO` and the related depth, stencil
       and HTILE registers, or both INFO registers cleared.
     - **`setViewport`, `0x014765e0`:** (command buffer, index, zmin, zmax, scale[3],
       offset[3]). It writes `PA_SC_VPORT_ZMIN/ZMAX` (`0xb4 + 2 × index`), then the six
       scale and offset floats from `PA_CL_VPORT_XSCALE` (`0x10f + 6 × index`).
     - **Draws:** the auto-index draw `0x014741b0` (command buffer, index count) and the
       other writers listed above.
     - **User data:** `0x01476420` (command buffer, stage, slot, value) writes one SGPR of a
       stage's user data: `SET_SH_REG` at a per-stage base register from a table at `0x04cd15c0`,
       plus the slot. The table's order gives the library's stage numbers: 0 compute, 1 pixel,
       2 vertex, 3 geometry, 4 export, 5 hull, 6 local (`COMPUTE_USER_DATA_0`, then
       `SPI_SHADER_USER_DATA_PS_0`, `_VS_0`, `_GS_0`, `_ES_0`, `_HS_0`, `_LS_0`). The writers
       of 2, 4 and 8 words (`0x01476390`, `0x014761a0`/`0x014762f0`, `0x01476240`) carry
       pointers and buffer and texture descriptors the same way.
     - **Multisample positions:** `0x014772c0` and `0x014773b0` write the 16 sample-location
       registers from `0x2fe`, plus `PA_SC_CENTROID_PRIORITY`.
     - **Clears** are ordinary draws with a clearing pixel shader on this GPU, so they need no
       path of their own. The depth and stencil clear values are context registers
       (`DB_DEPTH_CLEAR`, `DB_STENCIL_CLEAR`; already replaced, #321-#327).
   - **The shader register blocks**, found in the header of each shader file in the game's
     archive (`.vpo` vertex, `.ppo` pixel). Each word was identified by values worked out from
     the shader's own code (local counts, no game data in the repository):
     - **Vertex (7 words from header offset `0x3c`):** `SPI_SHADER_PGM_LO_VS`, `PGM_HI_VS`,
       `PGM_RSRC1_VS`, `PGM_RSRC2_VS`, `SPI_VS_OUT_CONFIG`, `SPI_SHADER_POS_FORMAT`,
       `PA_CL_VS_OUT_CNTL`.
       - The position format's non-zero fields match the exported positions in all 7,564
         vertex shaders that export one.
       - The export count matches the exported parameters in all but 5.
       - `RSRC1`'s register count covers every exported register.
       - In the file, the program address words hold placeholders (a small number, then
         `0xffffffff`); the loaded shader's address replaces them.
     - **What `pos1` carries:** in every shader that exports it (3,496), `PA_CL_VS_OUT_CNTL` is
       `0x400003`: clip distances 0 and 1 in the first clip/cull-distance vector. The extra
       position exports follow the order the register defines (the misc vector, then distance
       vectors 0 and 1), so `pos1` here is two clip distances.
     - **Pixel (12 words from `0x3c`):** `SPI_SHADER_PGM_LO_PS`, `PGM_HI_PS`, `PGM_RSRC1_PS`,
       `PGM_RSRC2_PS`, `SPI_SHADER_Z_FORMAT`, `SPI_SHADER_COL_FORMAT`, `SPI_PS_INPUT_ENA`,
       `SPI_PS_INPUT_ADDR`, `SPI_PS_IN_CONTROL`, `SPI_BARYC_CNTL`, `DB_SHADER_CONTROL`,
       `CB_SHADER_MASK`.
       - The colour format and shader mask match the exported targets in all 2,796 pixel
         shaders that export colour.
       - `NUM_INTERP` matches the attributes the code reads in 2,628 of them.
       - Every one enables the perspective-centre barycentrics first, so they arrive in `v0`
         and `v1`.
       - The inputs: 1,678 use only those barycentrics; 1,111 add the front-face flag; nine
         also read the pixel position.
       - The executor draws all three: the front-face VGPR (`SPI_PS_INPUT_ENA` bit 12) holds 1 or
         0 with `SPI_BARYC_CNTL`'s `FRONT_FACE_ALL_BITS`, otherwise a float whose sign says it
         (1.0 front, -1.0 back), as shadPS4 fills it. Which winding faces front comes from
         `PA_SU_SC_MODE_CNTL`, which is not observed yet: the reset state, counter-clockwise
         (Vulkan's area rule), is assumed.
     - **Confirmed at run time** (6 November 2026): the game passes these same blocks to
       `sceGnmSetVsShader` and `sceGnmSetPsShader`, with the code's address filled in. Those
       calls are the runtime's own, so they hand the renderer the shader directly: placed at the
       command-buffer address they write to, it joins the calls of the buffer submitted with that
       address (`rt_render_record_*_shader_at`). The game's vertex shaders pass a fetch-shader
       modifier, which replaces `PGM_RSRC1`'s SGPR and input-VGPR counts. A null pixel shader
       (a depth-only pass) is recorded too: such a draw is drawn with no pixel stage when it writes
       no colour target, and stops by name when it would.
   - **How the hooks attach:** the library's functions are being decompiled like the rest of the
     game, as replacements verified to write exactly the original packets. The renderer leaves
     those packets alone, so verification still holds. Each of these replacements also makes one
     observer call into the runtime: the render target's registers, the viewport, a shader's
     register block, the user data, and the draw. The runtime's renderer keeps that state and,
     at each draw, makes a Vulkan or Metal draw with the translated shaders, into images that
     stand for the game's render targets. The packets themselves still go nowhere, as they do
     now. Without the renderer the observer calls do nothing, so a boot without graphics behaves
     as before.
   - **Done on the runtime side:** the call record (`runtime/render_calls.h`): render targets,
     viewports, shader register blocks, user data and draws per command buffer, plus any context or
     user config register the library sets (`rt_render_record_register`: blend, depth and stencil
     control, colour control, the target mask, the primitive type) and the instance count. The
     executor understands those registers and, at each draw, stops by name on what it does not
     draw yet: depth or stencil testing, primitives other than triangle lists, colour modes other
     than a normal copy, more than one instance, and any register it does not interpret. A draw
     whose targets are all masked off (and that writes no depth) writes nothing and is skipped.
     - **Several render targets (MRT):** a draw writes the colour targets of every enabled slot
       0-7 whose `CB_TARGET_MASK` nibble (bits 4n to 4n+3: x, y, z, w, as shadPS4 hands them to
       Vulkan's colour write mask) is not 0, each with its own `CB_BLENDn_CONTROL`; slot n is
       colour attachment n, which the pixel shader's `mrt n` export writes, and a slot between
       two drawn ones is an unused attachment. The targets of one draw must have one size (others
       stop by name); partial masks write only their channels.
     - **Blending** (`CB_BLEND0_CONTROL`, with `CB_BLEND_RED`-`ALPHA` as Vulkan's blend constants):
       AMD's factor and function numbers (Mesa's `sid.h`, shadPS4's `regs_color.h`) map one to one
       onto Vulkan's; without `SEPARATE_ALPHA_BLEND` alpha uses the colour's. Dual-source factors
       stop by name. Each slot blends with its own `CB_BLENDn_CONTROL`.
   - **The draw executor** (being built): it runs a submitted buffer's recorded calls on the GPU.
     - **Submission runs beside the title** (`runtime/renderer/renderer.c`): `sceGnmSubmitCommandBuffers`
       and `sceGnmSubmitAndFlipCommandBuffers` read their packets, take a copy of the buffer's
       recorded calls (`rt_render_take`) and return at once; the renderer's own thread runs the
       submissions in order. What the guest can observe of the GPU's progress is a step after a
       buffer's calls (`rt_gpu_step`): its end-of-work and RELEASE_MEM writes, its WAIT_REG_MEM
       waits and the submit-and-flip's flip are performed only once the calls before them have run
       and drawn targets are written back, so the CPU never sees a label before the work, or reads
       memory the GPU writes before its batch is done. Descriptors and memory the draws read are
       read when they run, as the PS4's GPU reads them; the title keeps them valid until it sees the
       work's label. A video-out flip from the CPU, and a frame read for the display, wait for the
       submissions before them. A stop on the renderer's thread still names the submitting call and
       the shader. Before this, each submit ran its work on the calling thread: the engine's movie
       playback draws from the main thread while its render thread submits, and the render
       thread, held for tens of milliseconds by its own submit, still had the shared graphics
       context when the main thread drew (found at the opening movie, 10 November 2026).
     1. **Guest memory on the GPU.** Shaders reach memory through guest addresses: buffer
        descriptors and pointers in their user data. The game's GPU-visible memory is direct
        memory, a range of the runtime's pool (one host memory file).
        - **Placement (done):** the runtime places each GPU-visible map that has no address hint
          at a fixed base plus its pool offset (`runtime/gpu_memory.h`, #348).
        - **One buffer:** the renderer maps the whole pool a second time and gives it to the GPU
          as one buffer (Vulkan: `VK_EXT_external_memory_host` on that mapping; Metal: an
          `MTLBuffer` over the same pages, `newBufferWithBytesNoCopy`). So every such guest
          address `A` is at `A + d` on the GPU, for one distance `d` fixed for the run.
        - **In the translator (done):** it adds `d` to every address a shader forms
          (`address_offset` in its layouts, #346), baked in as a constant, since shaders are
          translated at run time once `d` is known.
        - **What a boot actually maps** (a local count, not committed):
          - fifteen direct maps, each of its range once, five of them GPU-visible (about 3.3 GiB);
          - six flexible maps, all CPU-only;
          - one map with an address hint: the tessellation-factor ring, at the address the
            runtime gives for it. The ring is read by the GPU's fixed-function hardware, not by
            shaders, so it can stay where the game asks.
        - **The cost, measured on an RTX 3070 (scratch test, not committed):** importing a
          memory-file mapping works, with a 4 KiB alignment and a GPU address. But the driver
          pins all of it, so the whole 5 GiB pool is held in RAM while the renderer runs. A boot
          without the renderer (`--display none`) doesn't import it. If the cost matters, a
          sparse buffer can keep the one distance while binding only the GPU-visible ranges, as
          they're mapped.
     2. **Push constants per stage.** The vertex and pixel shaders of a draw each get their own
        user data. The vertex shader's is at byte 0 of the push constants and the pixel
        shader's at byte 64 (`push_constant_offset`), 128 bytes in all, the size every Vulkan
        device guarantees.
     3. **Running a buffer** (begun: `runtime/render_executor.h`).
        The optional [Metal draw executor](macos-metal.md#draw-executor) uses the same call record
        and readback API, with its own explicitly limited profile; the following describes Vulkan.
        - **What runs today:** COLOR_8_8_8_8 render targets in slots 0-7 (UNORM or sRGB, either
          component order; COLOR_10_11_11 and COLOR_16_16_16_16 FLOAT too, written back to their
          memory as the hardware lays them out, though only 8_8_8_8 ones are read as BGRA), viewport
          0, vertex and pixel shaders with their user data, and
          auto-index draws as triangle lists.
        - **Rect lists** (primitive type 17, which the game's fullscreen passes use): Vulkan has no
          such primitive, so each rect's three vertices go through a generated geometry stage
          (`runtime/rect_list.h`) that adds the fourth corner. The right-angle vertex is the one
          whose x matches one neighbour's and y the other's, and the fourth corner is the other two
          minus it, for the position and every output (shadPS4's rule, facts only). A device
          without geometry shaders stops by name at a rect list; Metal will need another route.
        - **State across buffers:** the GPU keeps its registers, user data and shaders from one
          submitted buffer to the next (no submission resets them), so the executor keeps the state
          the calls set across runs too. The game's command buffers continue into new blocks as they
          fill (a buffer that sets a compute shader at its end, the next one dispatching it).
          `rt_executor_reset` forgets it, for tests' independent cases.
        - **Render targets keep their memory:** a render target's guest memory stays its contents,
          laid out by its tile mode (`runtime/tiling.h`): its image is loaded from the memory before a
          draw when the memory may have changed since (at each buffer, as the CPU runs between
          submissions, and after each dispatch, whose stores may reach it), and written back once drawn
          into, before anything reads the memory (a dispatch, a draw's images, the end of the buffer).
          So a pass can read what an earlier one drew as an image, and draws build on what a compute
          clear stored. The game's logo pass draws, blended, into the image its compute clear filled,
          which the fullscreen pass then reads. Detiling and tiling go a micro tile at a time (checked
          against the per-texel offsets for every mode and element size).
        - **Moving targets only when needed:** a target is written back before a dispatch, at the end of
          each buffer, and before a draw reads an image overlapping it, not after every draw: a draw's
          colour writes reach memory on the console too only when the game flushes the colour caches
          before reading. With these (and, then, copies by the CPU skipped while the guest memory held
          what the image and it last agreed on) the boot's frames went from 66 to about 1,440 in 90 s
          (RTX 3070), which reaches the title screen.
        - **One batch per buffer:** a buffer's draws, dispatches and copies are recorded into one Vulkan
          command buffer and submitted once, with barriers between them, instead of each waiting for the
          GPU. The CPU waits only where it reads what the batch produces: a render target written back
          (before a dispatch, before a draw reads its memory as an image, at the end of the buffer), guest
          memory a dispatch in the batch may have stored to (a descriptor read from memory, a load's
          comparison), a staging buffer the batch still copies from, and the run-time stop words, which are
          checked once the batch has run (each shader has its own, so a stop still names its shader). Each submitted buffer still ends with its batch run, so the CPU
          sees everything it drew when the submission returns. On the logo and title screens this alone
          changed no frame count: a profile puts about 75% of the time in the CPU's copies (tiling,
          detiling and comparing render targets), not in waiting.
        - **Copies on the GPU** (`runtime/tile_copy.h`): a render target's loads and write-backs, and the
          loads of images whose elements are whole 32-bit words (8_8_8_8, 32-bit formats, the BC
          blocks), are detiled and tiled by a compute shader that reads and writes the guest memory
          buffer directly, in the batch: one invocation per element, its place from a table of the
          layout's offsets that `runtime/tiling.h` works out (each micro tile's first element, and the
          64 places within a micro tile, `rt_tiling_micro_spread`), so the GPU's placement is the CPU
          code's by construction. Each group of 64 takes one micro tile with its lanes in memory order,
          so neighbouring lanes touch neighbouring guest memory (taken in row order instead, the copies
          cost about twice the GPU time, as host memory is read and written across PCIe). Nothing waits for them: the batch notes the memory each write-back
          stores to, and the CPU waits only before reading that memory itself. A target is loaded
          again, and such an image too, whenever the memory may have changed (the memory epoch: a new
          buffer, a dispatch, a write-back over it), without comparing bytes: reading it on the GPU
          costs less than comparing it on the CPU. Images of 8- and 16-bit elements (the title's glyph
          atlas) are still detiled by the CPU, skipped while the memory holds what was last loaded.
          Showing a frame copies the target's image to a host-visible buffer once per flip.
          `test_render_executor` checks a 1D-tiled target's texels at `rt_tiling_offset` after a
          write-back and a CPU write showing at its pixel after a load; a mutated table fails both.
        - **Unset user data stops:** the translator reports the user SGPRs a program reads before it
          writes them (in program order), and the executor tracks the slots the calls have set since
          the GPU's reset. A shader reading a slot no call has set, or a descriptor or descriptor
          pointer in such slots, stops by name instead of running on zeros (a null descriptor can
          lose the device).
        - **The logo pass's inputs:** its vertex shaders' user data come through a further writer,
          `0x014764a0` (command buffer, stage, slot, words, count; after the NOP marker `0x6875000d`),
          now observed; their fetch shaders load vertex colours from 8_8_8_8 unorm buffers, each byte as
          v / 255 correctly rounded (a table worked out in single precision, since a shader's division
          need not be exact), with the descriptor's DST_SEL; its textures are block-compressed (BC7),
          loaded in 4 x 4 blocks (pitch, width and height counted in blocks, as shadPS4 counts them) as
          Vulkan's BC formats: BC1 (with its one-bit alpha), BC2, BC3, BC7 unorm and sRGB, BC4 and BC5
          unorm and snorm; BC6 stops by name. The title screen adds an 8-bit unorm image (DATA_FORMAT
          1, its glyph atlas, linear aligned), loaded as R8.
        - **Indexed draws:** `INDEX_BASE` (`0x014752c0`), `INDEX_BUFFER_SIZE` (`0x01475320`),
          `INDEX_TYPE` (`0x01475270`) and `DRAW_INDEX_OFFSET_2` (`0x01474420`) are observed and
          recorded; the draw binds the guest memory buffer as Vulkan's index buffer from the base plus
          the first index, 16- or 32-bit indices (VGT_INDEX_TYPE; swaps stop by name). The packet's
          `MAX_SIZE`, which the library sets to the count, is taken as counting from `INDEX_OFFSET`, as
          shadPS4 reads it and the game's draws need (they start past it): inferred, not documented.
          The game's logo pass draws this way, blended, into the image its fullscreen pass then reads.
        - **Depth targets:** the depth target's setter (`0x014739b0`, observed)
          reports the registers it writes (`DB_Z_INFO` to `DB_DEPTH_SLICE`, `DB_DEPTH_VIEW`, ...), the
          stencil reference setters (`0x01473190`, `0x014731f0`) `DB_STENCILREFMASK` and `_BF`, and the
          replacements writing `DB_RENDER_CONTROL`, `DB_DEPTH_CLEAR` and `DB_STENCIL_CLEAR` report
          theirs. A draw that tests depth or stencil with a buffer bound gets an executor-owned depth
          image (Z_16 or Z_32_FLOAT, with or without 8-bit stencil, found by its write addresses and
          sized from `DB_DEPTH_SIZE`; one larger than the colour target, as the game pads it, is drawn
          at the colour target's size, and a smaller one stops) and Vulkan depth and stencil state; with none bound (format 0,
          as switching the target off writes) the test has nothing to work on and the draw goes on
          as if it were off (shadPS4 takes it the same way). Compare functions are AMD's CompareFrag
          order, which is Vulkan's. Done: every compare function, and writes (depth writes; stencil
          keep, zero, replace with the test value, invert, and add or subtract, clamped or wrapping,
          when they step by `STENCILOPVAL` 1, which is Vulkan's increment and decrement). A test that reads the buffer compares with what
          earlier draws wrote into the depth image; one reading a depth image no draw has written yet
          stops by name, as do other stencil operations and steps, depth bounds and `DB_RENDER_CONTROL`'s
          clears, so the depth image's starting contents (and the HTILE metadata the game may clear
          it with) are never seen. The buffer's contents in guest memory are never loaded: a depth
          or stencil buffer the CPU or a compute shader writes would not be seen (not found yet). A draw that writes only the depth target (target mask 0, or
          `CB_COLOR_CONTROL`'s mode `CB_DISABLE`) draws without a colour target; one that writes
          nothing is skipped. Triangle strips (`VGT_PRIMITIVE_TYPE` 6) are drawn too. A view of one
          slice of an array depth target (`DB_DEPTH_VIEW` SLICE_START = SLICE_MAX) draws into an image
          kept for that slice alone; a view of several slices stops by name.
        - **Not yet:** other formats, more
          render targets and other pixel inputs. These stop with the reason.
        - **The image's memory order:** an image's pixels only leave the GPU through
          `rt_executor_read_target`, which gives the display's BGRA either way. So nothing yet shows
          whether a SWAP_ALT target is kept blue-first, as the console stores it. That matters once
          images go back into guest memory. At `sceGnmSubmitCommandBuffers`, the executor takes each buffer's
        calls (`rt_render_submitted`) and keeps the current state: render targets, viewport,
        shaders, user data. At each draw it translates the two shaders from their code
        addresses (layouts from their register blocks; translations cached by code and layout),
        makes or reuses a pipeline, and draws into images that stand for the render targets,
        found by their addresses.
     4. **Wired into the runtime** (`runtime/renderer.h`): with the display on
        (`pbboot --display headless|window`, in a build with Vulkan), each buffer
        `sceGnmSubmitCommandBuffers` or `sceGnmSubmitAndFlipCommandBuffers` submits has its recorded
        calls run, and at a flip video out shows what was drawn into the flipped buffer's address,
        in place of the black frame. The executor opens at the first buffer that has recorded calls:
        giving the GPU the 5 GiB pool takes about 2.4 s (measured on an RTX 3070), long enough to
        change which thread reaches its first unimplemented call first if it happened at every
        boot. Recorded draws execute only the supported state; missing targets, unsupported
        shaders and unimplemented modes stop with a reason. This does not establish a working
        game frame.
     5. **The observer calls** in the library's replacements (begun). Replacements call
        `runtime/render_observer.h`, which finds the record in the boot harness (`pbboot` exports it)
        and does nothing under a host without it, so the replacements' verification is unchanged.
        The register setters (blend, colour control, target mask, depth and stencil control, the
        primitive type), the instance count, the viewport and the auto-index draw report now.
        `tools/boot.py --game-lib build/game/libbbgame.so --no-record` runs a boot with the
        replacements, and with the display on the game's first draw reaches the executor: a
        fullscreen pass drawn as a rect list (primitive type 17), which stops by name until the
        executor draws rect lists. **Observe hooks** (`runtime/observe_hooks.h`) report what has no replacement yet:
        the hook calls an observer with the call's arguments, then the original runs from its
        first instructions relocated next to the image, so every packet is still the original's.
        A replacement, when one lands, takes the address and its observe hook is dropped. They
        cover `setRenderTarget` (`0x014738b0`) and the five user-data writers (`0x01476420`
        one word, `0x01476390` two, `0x014761a0` and `0x014762f0` four, `0x01476240` eight),
        whose arguments come from their disassembly (`game/render/observe_gpu_library.c`). With
        them the game's frame reaches its compute passes' user data, which stops by name until the
        executor runs compute. **Compute** runs too: `sceGnmSetCsShader` hands the renderer
        its 7-word register block (`COMPUTE_PGM_LO/HI`, `RSRC1/2`, `NUM_THREAD_X/Y/Z`, the order
        shadPS4's `gnmdriver.cpp` writes them), placed like the other shaders; the dispatch writers
        `0x01474c50` and `0x0148a350` (command buffer, x, y, z) are observed; and the executor
        translates the shader for its workgroup size and runs the dispatch, its writes in the guest
        memory before the next call. A workgroup's y or z index and its size information stop by
        name. The two dispatch writers with a fifth argument (`0x01474d10`, `0x0148a410`) are not
        observed yet. Compute shaders' **images** are executor-owned Vulkan images
        found by their descriptor's address and shape: an image the GPU writes stays there and is
        never tiled back into guest memory; a new image whose first use writes it starts cleared.
        An image no shader has written holds the guest memory's texels, detiled with
        `runtime/tiling.h` and loaded again at a use that reads it when the guest memory changed since
        (the CPU or a buffer store may have changed them); one that is also a render target stops by name. Pixel shaders' images
        are found the same way and bound as sampled images. Formats: 32 (float, uint, sint), 32_32 and 32_32_32_32 float, 8_8_8_8
        unorm and uint, 8 and 8_8 unorm; 1D and 2D images and their arrays, one level, a view of any of an array's layers
        (slices count from `BASE_ARRAY`, as shadPS4 and Mesa's radeonsi have it), DST_SEL in place.
        On the game, all of the boot's compute passes now run (two clears and a buffer-to-image
        copy into a 3-layer 1D array), and the next stop is a draw whose pixel shader reads the
        pixel position.
        Still to report: indexed draws; then follow the auto-index draw wrapper's callers
        (`0x015fbb50`) up to the title screen's 2D passes.

### Indexed draw packet fields

The record keeps index-buffer state (`INDEX_BASE`, `INDEX_BUFFER_SIZE` and
`INDEX_TYPE`) and distinguishes offset draws (`DRAW_INDEX_OFFSET_2`) from addressed
draws (`DRAW_INDEX_2`). The recorded base is the byte address made from the two
INDEX_BASE DWORDs, without masking either word. The executor rejects an unaligned
address or a range outside GPU-visible memory. The recorder never reads index memory.

An offset draw recorded through the existing first/count API has
`has_packet_fields = 0` and retains its `INDEX_BUFFER_SIZE` bound. The packet API
sets that tag to 1 and also records the emitted header, `MAX_SIZE` and
`DRAW_INITIATOR`. Even a zero header remains a packet call and is rejected as an
unsupported header. A packet's MAX_SIZE counts from its first index, independently
of INDEX_BUFFER_SIZE. Counts above MAX_SIZE would require DMA zero filling, which
the executor does not implement.

Vulkan draws supported offset packets. Predicated packets, other headers and
nonzero initiators fail with a reason. Addressed DRAW_INDEX_2 calls are recorded
with their complete payload but are not yet executed by Vulkan. The packet
observer bridge belongs with the GPU-library replacements that first call it.
